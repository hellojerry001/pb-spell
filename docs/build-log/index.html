为什么不能只给一个转圈

npm run tauri build 动辄几分钟，而且失败原因全在 cargo 的输出里： 缺 Xcode 命令行工具、签名失败、Node 版本不对、前端构建报错……。 只显示「打包失败」等于把排查工作全丢回给用户 —— 他还得自己去终端再跑一遍。

所以这里固定是两行结构：

  • .build-status —— 一行状态：进行中显示转圈 + 已用秒数，结束时转 is-ok / is-bad；
  • .build-log —— 等宽日志块，固定高度滚动，始终跟在最后 30 行。

几个刻意的选择

选择原因
日志块设 user-select: text应用外壳全局 user-select: none，但报错是要复制出去搜的
只取尾部 30 行cargo 输出极长，前端传全量没意义；真要全量去 ~/.portbutler/logs/<id>.build.log
高度用 --build-log-h（240px）定高才能滚动，否则日志越长弹窗越长，按钮被顶出屏幕
关窗不杀进程打包可能要几分钟，用户不该被「必须盯着」绑架；下次点开继续看
完成后才显示「在访达中显示」.dmg 在 src-tauri/target/release/bundle/dmg/，路径很深，手翻很烦

状态行不是 .hint

.hint 是表单下方的补充说明，颜色最弱（--c-text-3）。 状态行要能托住 10px 的转圈并说清当前在做的事，所以抽成独立的 .build-status： display: flex 让转圈与文字基线对齐，颜色取 --c-text-2， 完成 / 失败再覆写成 --c-ok-strong / --c-danger。

弹窗先停在配置态

打包前有两件事要定：应用图标与应用名（写 tauri.conf.json 的 productName）。 它们都不是独立功能，所以直接住在弹窗的第一态里：

态判断依据底部按钮
配置态build_status.running === false取消 / 开始打包
打包态build_status.running === true在访达中显示 / 终止打包 / 关闭

openBuild() 打开时先探一次 build_status：上次关了窗口但打包还在跑，就直接进打包态接着看， 不会要求用户把图标和名字再配一遍。

两态的底部按钮是同一组 DOM，按态切 hidden —— 不是两份 markup。注意 hidden 属性只是 UA 样式里的 display: none，任何作者样式一旦给该元素写上 display（.btn 这种） 就会把它顶掉，所以外壳里兜了一条 [hidden] { display: none !important; }。

配置项的落盘时机

各自贴着最自然的那个动作：

配置项什么时候写盘为什么
应用图标选完图立即写（swap_icon）生成整套尺寸本来就是个完整动作，顺带热更新已构建的 .app
应用名称输入框失焦 / 回车写（set_app_name）即时保存，不丢改动；写失败回滚输入框，别显示一个没落盘的名字

「开始打包」也会兜一次名字：若输入框里的值与已落盘的不同，先写盘再起进程—— 产物名和用户看到的名字必须一致，宁可拒绝打包也不产出一个名字对不上的 .app。

后端为什么是轮询

打包不能作为同步命令返回（前端会傻等几分钟）。分工是：

build_dmg     → 拉起进程组，立刻返回 pid
build_status  → { running, tail, dmg, bundleDir }   ← 前端每 1.5s 问一次
cancel_build  → 杀整个进程组

tail 由后端读日志文件末尾若干行并剥掉 ANSI 转义（cargo 输出带颜色， 原样展示会变成 [41;31m 这种乱码）。dmg 则是递归扫 src-tauri/target/{release,debug}/bundle/ 找最新的 .dmg —— 找到了就说明成功了， 不必去解析 cargo 的文本输出。
